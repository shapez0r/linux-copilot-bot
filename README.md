# Copilot Telegram Bot

A Telegram bot for an Ubuntu VM that turns chat messages from authorized users into repository changes. For each request it:

1. selects an existing GitHub repository and clones it, or creates a new one from a selected local app template (`eurofish` by default), at `/home/localadmin/repos/<name>`;
2. takes the message as the prompt;
3. sends the repository to Copilot Chat through the Playwright round-trip engine and applies the returned repository; once the Copilot prompt has ended, the engine deletes the **Microsoft Copilot Chat Files** folder from the signed-in account's OneDrive and empties its recycle bin;
4. commits and pushes the result to GitHub;
5. registers and restarts an enabled systemd system service that runs `make run` from `/home/localadmin/repos/<name>`;
6. for `/new`, allocates the next tunnel port and creates the Cloudflare route.

**Experimental:** the engine drives Copilot's and OneDrive's browser UIs, so UI changes can interrupt it. Changes are pushed without review; review the commits on GitHub afterwards.

## Requirements

- Ubuntu with Python 3.9+, `python3-venv`, Git, and `make`.
- An account with access to Copilot Chat.
- A Telegram bot token from [@BotFather](https://t.me/BotFather) and the numeric Telegram user id of each administrator (for example from @userinfobot). Regular users request access in the bot.
- A GitHub token with read/write access to repository contents. Creating repositories requires permission to create repositories for the owner, and `/delete` requires permission to delete repositories.
- A local app checkout to use as a new-repository template. The default is `<REPOS_DIR>/eurofish` (`/home/localadmin/repos/eurofish` with the default configuration).
- For `/new`, route commands, and the tunnel portion of `/delete`, a remotely managed Cloudflare Tunnel and an API token with **Account / Cloudflare Tunnel / Edit** and **Zone / DNS / Edit** permissions.
- systemd and non-interactive `sudo` permission for the bot's Linux account to install, remove, enable, and control its system services.

## Setup

```bash
make setup          # virtual environment, Playwright, Chromium
make system-deps    # Chromium's operating-system libraries (sudo)
sudo mkdir -p /home/localadmin/repos && sudo chown "$USER" /home/localadmin/repos
cp .env.example .env && chmod 600 .env   # then fill in the required values
make login          # sign in to Copilot once (see below)
make run            # first run uses sudo to register and enable the bot service
```

Put the Cloudflare API token, account ID, and zone ID in `.env` to use `/new` or `/cloudflare` and to let `/delete` remove tunnel routes. Without those settings, `/delete` still attempts the GitHub and local cleanup and reports that it skipped the route. The tunnel is always `kurwalab-tunnel` and the domain is always `kurwalab.fyi`. Ordinary redeployment never changes routes; only these commands do.

### Signing in to Copilot

`make login` opens a visible Chromium window; sign in, open a usable Copilot Chat page, and press Enter in the terminal. The profile (default `~/.copilot-repo-browser`) holds authentication state: keep it private. Bot runs use the same profile; a run that starts while another session's browser has it open uses a private temporary copy (see [Sessions](#sessions)). Browser visibility defaults to `BOT_SHOW_BROWSER` and can be overridden for one request with `browser` or `nobrowser` in `/fix`. On Linux without `DISPLAY` or `WAYLAND_DISPLAY`, a requested visible bot run falls back to hidden Chromium instead of failing; `make login` still requires a display.

A VM usually has no display. Either run `make login` over `ssh -X` (or a VNC session), or sign in on a Linux desktop and copy the profile directory to the VM. A copied profile may not be accepted by Copilot; if so, sign in on the VM. Profiles from Windows or macOS do not carry over. Run `make login` while no session is running or the bot is stopped, and repeat it when a run fails with an authentication error.

### Running as a service

The first foreground `make run` uses non-interactive `sudo` to install and enable `/etc/systemd/system/copilot-telegram-bot.service` unless the bot is already running under systemd. It does not start a duplicate process. Only one bot process runs per `STATE_DIR`: each process holds an exclusive lock on `<STATE_DIR>/bot.lock`, and a second `make run` (for example a foreground run while the service is active) exits with an error instead of polling Telegram alongside the first, which would split messages between the two processes and break guided flows. Configure the bot account for passwordless access to the required `install`, `rm`, and `systemctl` commands so registration and later app management can run without a terminal. Stop the foreground run, then start the registered service:

```bash
sudo systemctl start copilot-telegram-bot
sudo systemctl status copilot-telegram-bot
```

The generated unit runs under the account that launched the bot, sets the repository as `WorkingDirectory`, and starts it with `make run`. `deploy/copilot-telegram-bot.service` is an equivalent editable template whose `User`, `Group`, `HOME`, and paths must match the installation account. Enabled services start at boot through `multi-user.target`. The bot and app services use the checked-out files as they are; they do not run `git pull` during startup.

## Using the bot

The bot works only in private chats; messages in groups and channels are ignored. Administrators are the user ids listed in `TELEGRAM_ADMIN_IDS` (comma-separated; `TELEGRAM_OWNER_ID` remains accepted as an alias). Everyone else becomes a regular user only after an administrator approves an access request:

1. Any Telegram user who sends `/start` gets a welcome message and a **🔑 Request access** button. Until approved, every other message, command, button, or file gets only a short reply together with that button; nothing else runs and files are not downloaded.
2. Tapping the button adds the user's numeric id, name, and username to the request queue and notifies every administrator. Repeated taps while a request is pending do not notify again, and the queue holds at most 100 pending requests.
3. Administrators in admin view open the queue with **📨 Access requests** (or `/requests`), pick a request, and choose **✅ Approve access** or **🚫 Reject request**; `/approve <id>` and `/reject <id>` do the same. `/approve <id>` also grants access to a user who has not sent a request.
4. An approved user receives the regular-user menu right away. A rejected user is told and may request access again. `/revoke <id>` removes an approved user's access and discards their open dialog and held files; apps they created keep their owner record.

Approved users and pending requests are stored in `STATE_DIR` and persist across restarts.

Administrators have every bot permission. Regular users can create apps, list all apps, fix apps they created, and start or stop only their own apps. Administrators can start or stop any app, register services for existing app folders, and change the bot itself (see [Changing the bot](#changing-the-bot)). The app list opens with a status summary (for example 🟢 2 running · ⚪ 3 stopped) followed by one card per app: a status icon, the bold name, and the status, with the public URL beneath as plain text that Telegram links itself, so tapping it opens the app without a confirmation prompt; admin cards also show the tunnel port and folder. Long lists are split into complete HTML messages that repeat a short heading. The app list is built from every direct folder under `REPOS_DIR` except the bot repository, including stopped or untracked apps; administrators also see the bot's own `linux-copilot-bot` entry. Its status comes from systemd and distinguishes running, stopped, failed, transitional, and unregistered services. Administrators see each app's name, status, full folder, tunnel port, and tunnel URL; regular users see its name, a plain status (running, starting, or stopped, or unavailable when it cannot be read), and public URL. Messages to regular users identify apps only by name and public URL and describe them only as started, running, or stopped: they never mention systemd, services, or process ids, omit deployment and tunnel sections, tunnel routes and ports, and server paths, and report failures in those areas generically. Messages to administrators keep service names, process ids, and detailed states but do not mention systemd either; for example, a redeploy is shown as restarting the app. The bot repository never appears to regular users (or to administrators in user view): it is left out of their app list, fix and start/stop choices, and template choices, and their requests for it are refused like requests for any app they do not own. Each created app is recorded with an owner: regular-user apps belong to the creating Telegram user id, while administrator-created and newly registered existing apps are owned by `kurwalab.fyi admins`. Active repositories are stored per Telegram user, the selected default model is shared, and each user runs at most one session at a time (see [Sessions](#sessions)).

Administrators can switch between **admin view** and **user view** at any time with the **👤 Switch to user view** and **🛡 Switch to admin view** buttons, which are always in their main menu. In user view, an administrator sees and uses the bot exactly as a regular user: the regular-user menu, help, listings, messages, and permissions apply, admin-only commands and buttons are refused, and apps created in that view are public and owned by the administrator's Telegram user id. The choice is stored per administrator and persists across restarts. Regular users cannot switch views.

Send `/start` to get a welcome message with a role-specific persistent keyboard, or `/menu` for the keyboard alone. The welcome message is a short greeting that ends with `Use the buttons below.`; it describes no buttons or commands, and the keyboard shows only the buttons the sender can use. Administrators in user view also get a note on switching back. Every main menu has a **/cli** button that lists the commands available to the sender, the same as `/help`. Any other message outside a guided step, including free text, an unknown command, or a message without text or files, starts nothing and gets the same welcome message after a short note (for example `Unknown command: /foo.`), so a fresh chat always starts from the menu (or, for users without access, from the **🔑 Request access** button). Regular users see creation, listing, fixing, and start/stop controls for their apps; administrators in admin view also see service registration, access requests, deletion, tunnel-management, and **🧵 Running sessions** options, and every administrator menu includes the view switch. The guided **Create an app** flow:

1. asks for a lowercase app name;
2. checks the models available in Copilot (see below) and offers them for selection;
3. loads template choices from local HTTP routes on the configured Cloudflare tunnel and keeps only apps that also have a local checkout under `REPOS_DIR`;
4. for administrators, offers a choice between a private (default) and a public GitHub repository; regular users skip this step and always get a public repository;
5. for administrators, offers a choice between a **Temporary chat**, which is not saved in Copilot, and a **Regular chat**, which stays in the Copilot chat history; regular users skip this step and use `BOT_TEMPORARY_CHAT`;
6. explains that the template's styling, architecture, and stack are retained by default but can be changed in the app description;
7. accepts the description, together with any files attached as described in [Attaching files](#attaching-files), then shows the existing edited progress message while Copilot builds, commits, deploys, and publishes the app;
8. returns the final public app link when provisioning succeeds.

The guided **Fix an app** flow offers the apps the sender may fix that have a folder under `REPOS_DIR` (the same folders `/list` shows), so ownership records of apps without a local checkout are not offered. Its buttons show only app names, and a repository can still be typed as `name` or `owner/name`; the **Delete an app** picker uses the same rule, and a name can still be typed. The flow then checks the available models, accepts the chosen model, lets administrators choose a temporary or regular Copilot chat, accepts the fix request and any attached files, and then runs, commits, pushes, and redeploys the app with those choices. The chosen model and chat type apply only to that request; the shared model set with `/model` is unchanged, and regular users always use `BOT_TEMPORARY_CHAT`. `/fix` accepts the same choices in one message: `app=`, `model=`, `prompt=`, and, for administrators, `tempchat` or `notempchat`, just as `/new` mirrors **Create an app**. It has a single form, and `app=` and `prompt=` are always required.

#### Attaching files

Administrators and regular users can attach any files, such as screenshots, photos, documents, logs, audio, or video, to a request that creates or fixes an app. Send them to the bot before the request text, at any step of the guided flows, or with a caption: the caption is handled as the request text (for example `/fix app=app prompt="<request>"`, `/new name=app prompt="..."`, or the description in a guided flow), and the files in a Telegram album are all attached to the album's caption. Files without a caption are held for the sender's next create or fix request, which uses and then clears them; the bot confirms the files it is holding. Up to 10 files can be attached to one request, and each file must be at most 20 MB, the largest file a Telegram bot can download. **Cancel / stop**, `/cancel`, and **Main menu** discard held files.

When the request runs, the bot downloads the files into a temporary folder under `STATE_DIR`, attaches them to the Copilot prompt after the repository archive, and removes the folder when the round-trip ends. For `/new`, the files are downloaded before the repository is created, so a failed download stops the request without creating anything. Copilot is told that the files are context and not part of the repository; they are not committed. Copilot must accept each file type: a file it refuses fails the request with an error.

Before either flow offers models, the bot opens Copilot with the browser profile, reads the **Claude** and **GPT** submenus of the model picker, and shows every enabled entry as a `provider/model` button, such as `Claude/Opus 5.5`. The check runs as the user's session and can be stopped with **Cancel / stop**. If the picker cannot be read, the bot reports why and offers `Claude/Sonnet 5.5`, `Claude/Opus 5.5`, `GPT/GPT-6`, `GPT/GPT-6.1 Sol`, or a free-form provider/model value instead.

Apps created by regular users are public GitHub repositories. Apps created by administrators are private unless the administrator chooses a public repository in the guided flow or passes `public` to `/new`. The administrator menu also provides app service registration and controls, confirmed app deletion, and Cloudflare route management. Repository selection, the shared model, and status are available through `/repo`, `/model`, and `/status`. Command forms remain available for automation and direct use, subject to the same permissions.

### New repository template

For every missing repository, the bot creates an empty GitHub repository, copies a local template app into the new checkout, excludes every `.git` entry, and pushes the copy as the single `Initial commit`. `/repo` always uses `<REPOS_DIR>/eurofish`; `/new` uses that default unless `template=<app>` selects another directory under `<REPOS_DIR>`. The template must exist and contain files that Git can commit. The guided creation flow derives its template buttons from one-label hostnames under `kurwalab.fyi` that route to local HTTP ports and have matching local app directories. `/new` then reads the ordered tunnel ingress list, chooses one more than the last local HTTP route port (or `8080` when none exists), selects its per-command model or the active model, and tells Copilot to preserve the selected template's architecture, stack, and styling by default while honoring requested changes. App and template names must be lowercase DNS labels containing only letters, digits, and hyphens.

Progress is shown in a single message per session that is edited as the session advances. Its first line is `Currently doing: ...`, using the latest visible reasoning paragraph, active step, task, or bot stage; once Copilot output is shown, the next line is `Repository: https://github.com/<owner>/<name>`. Each displayed bot stage, task, plan item, activity, and step carries a stable first-seen timestamp in the bot host's local time, formatted as `HH:MM:SS`. A compact stage is shown until Copilot exposes structured output, then the current task and plan, activity or step names, reasoning-duration labels such as `Reasoned for 12s`, and interleaved live answers take its place. Live answers, activity sections, and task cards are read from the whole page, including open shadow roots and same-origin frames. Answers come from Copilot's response messages or, when those are not marked or contain no readable text, from the content that follows the submitted prompt. Visible reasoning text is not discarded: the latest part of each reasoning passage is placed under its step in a collapsed Telegram quote block marked 💭, which expands when tapped. The progress message is sent as Telegram HTML, and when it grows too long the oldest lines are dropped. Code-execution details are omitted, including code blocks, editors, monospace preformatted output, and fenced code. While Copilot is responding, the last line of the message is a ⏳ heartbeat refreshed every 15 seconds with the current timestamp: it states that the prompt is still running when a Stop control is visible or the output recently changed, and otherwise how long neither has been seen against the 30-second limit. A prompt is treated as running for as long as a Stop control is visible in the current task card (revealed by hovering it) or near the prompt input, even when no new output is detected. When neither control is visible and no new output, task-card change, or Stop-control change is detected for 30 seconds (detection starts after submission and covers the whole page, including open shadow roots and same-origin frames), the run fails with `Copilot failed to provide an answer, the running prompt was not responding for 30s`. Ordinary requests end with the commit, a diff-style change list, the redeploy result, and Copilot's final answer (the text after its last activity section, without interim answers or code). The change list resembles an editor's diff view: a total line with 🟢 `+` insertions and 🔴 `−` deletions, then one 📄 line per changed file (up to 20) with its numbers of additions and deletions; binary files are marked `binary`. The counts come from the pushed commit, so new files are included. Regular users also get the app URL instead of the redeploy details. `/new` returns the commit, provisioning status, public app URL, and Copilot's final answer, with the `Deploy:` and `Tunnel:` lines shown only to administrators. Every create or fix result message, including one that reports no changes, ends with that answer under `Copilot output:`, or `(no final text returned)` when Copilot gave none.

### Sessions

Each create, fix, model check, deletion, or other bot job runs as a session. Every user, administrator or regular user, runs at most one session at a time, and sessions of different users run in parallel, each with its own Copilot browser and progress message. A user who starts another job while their session runs is told to wait or use **Cancel / stop**. Two sessions never work on the same app at once: a request for an app that another session is changing is refused until that session ends. App creations that run in parallel reserve distinct tunnel ports, so each new app gets its own port.

Chromium lets only one process use a browser profile. The first running session uses `COPILOT_PROFILE` itself, so sign-in state that Copilot refreshes is kept; a session that starts while that profile is open runs on a temporary copy under `STATE_DIR` (without Chromium's lock files and caches), which is deleted when the session ends. Sign-in changes made in a copy are not kept.

Administrators in admin view open **🧵 Running sessions** (or `/sessions`) to see every running session: its number, user, action, start time, and duration. Each session has a **⏹ Stop session #<number>** button; stopping asks Copilot to stop and tells the session's user. Actions that do not use Copilot, such as a deletion, finish their current step first. `/cancel` stops only the sender's own session, and `/revoke` also stops the revoked user's session.

### What a request does

- **Prepare:** the checkout must be on a branch with no uncommitted changes; the bot fast-forwards it to `origin`. A mode-only change of `bin/git-askpass` in the bot's own checkout is reverted first; any other change still stops the request.
- **Round-trip:** the engine opens a new Copilot chat for every request, whether temporary or saved, so no earlier conversation is continued. It uploads a ZIP of the committed `HEAD`. For fixes it adds a `.git` directory holding the checked-out branch's history (without remotes, hooks, or reflogs), so Copilot can read earlier changes with `git log`; for `/new` the archive has no `.git` directory and the prompt does not mention Git history, so each new app starts fresh. It asks Copilot for the complete fixed repository without a `.git` directory, rejects a returned ZIP that contains one, validates the rest, and replaces the worktree. Attached files are uploaded with the archive as context. The bot appends a note asking Copilot to keep a Makefile whose `run` target starts one HTTP server in the foreground and to keep secrets and runtime data outside the repository.
- **OneDrive cleanup:** after every submitted prompt ends, whether it succeeded, failed, or was stopped, the engine cleans up OneDrive in the same signed-in browser before closing it. Copilot stores the uploaded archive and attachments in the **Microsoft Copilot Chat Files** folder of the signed-in account's OneDrive. The engine opens `https://kurwalabb-my.sharepoint.com/my` (choosing the signed-in account if Microsoft asks; switching to **My files** if another view opens) and finds that folder by its exact name (ignoring the marker icon OneDrive shows beside recently changed items) together with its folder icon or item count, scrolling the list if needed. Like a user, it moves the mouse over the folder's row so OneDrive shows the round row check left of the folder icon, clicks the check (clearing any other selected item first), clicks **Delete** in the command bar, and confirms with the dialog's **Delete**. If no **Delete** command appears, it presses the Delete key, and then uses **Delete** from the folder's context menu. Deletion stops if OneDrive reports more selected items than the folder. It then opens `https://kurwalabb-my.sharepoint.com/recycle`, clicks **Empty recycle bin**, and confirms with the dialog's **Yes** (or **Delete**). Lists without grid or table rows, and lists rendered inside frames or open shadow roots, are handled, and the recycle bin is emptied even if the folder deletion fails. All other files and folders in My files are kept, but emptying the recycle bin permanently deletes every item in it, not only Copilot files. Cleanup is best effort: its progress and any failure are shown as status lines, a failure does not fail the request, and anything left behind (for example when a stopped session ends before cleanup finishes) is removed after a later prompt. The model check submits no prompt and does not clean up.
- **Commit and push:** all changes are committed on the current branch with the first line of the request as the subject and a body holding the request followed by Copilot's final answer without code (tokens redacted), and pushed to `origin`. Later fix requests upload this history, starting with the new app's first commit, so Copilot can see what each earlier change did. If Copilot changed nothing, nothing is committed or deployed. A failed push leaves the commit locally and is reported; the next request pushes it.
- **Redeploy:** the bot uses non-interactive `sudo` to write `/etc/systemd/system/copilot-app-<name>.service` when it does not exist yet and to enable it, then asks systemd to restart it. An existing unit file is never rewritten when an app is redeployed, started, stopped, or registered, so manual edits to it are kept; to regenerate it, remove it and start the app again. The generated unit sets the app repository as `WorkingDirectory`, executes `make run`, restarts on failure, removes bot secrets from its environment, and appends output to `<STATE_DIR>/logs/<name>.log`. The redeploy counts as successful only when systemd reports the service active through `DEPLOY_SETTLE_SECONDS`; otherwise the service state and log tail are sent. A repository without a usable `run` target is pushed but not started.
- **New-app publish:** after a successful `/new` service restart, the bot creates `<name>.kurwalab.fyi` on `kurwalab-tunnel`, targeting the allocated `127.0.0.1` port. If deployment or routing fails, the report identifies the completed and failed stages.
- **App deletion:** `/delete app` independently attempts to stop, disable, and remove its systemd unit, delete its GitHub repository, remove a matching verified checkout at `<REPOS_DIR>/app`, and delete its Cloudflare route and tunnel CNAME. The matching reboot crontab line is also removed when present. Missing resources need no cleanup. Every step is reported, and a failure or missing Cloudflare configuration does not block the other attempts.
- **Routes on demand:** `/cloudflare eurofish 8080` creates or updates `eurofish.kurwalab.fyi` to `http://127.0.0.1:8080` on `kurwalab-tunnel` and maintains its proxied DNS CNAME. `/cloudflare list` shows named ingress rules, and `/cloudflare delete eurofish` removes that ingress rule and its matching tunnel CNAME. Route names must be one lowercase DNS label, and ports must be 1–65535. Other ingress rules are preserved. Ordinary deployment never changes routes.

**Important:** the engine applies a returned ZIP as a full replacement. Everything in the checkout except `.git` is replaced, including untracked and ignored files such as `.env`, virtual environments, `node_modules`, and local databases. Keep runtime data and secrets outside the checkout and let `make run` rebuild dependencies.

### Changing the bot

The bot's own checkout, `<REPOS_DIR>/linux-copilot-bot`, can be changed only by administrators in admin view, through **Fix an app** or `/fix app=linux-copilot-bot prompt="<request>"`. A bare `linux-copilot-bot` name resolves to the GitHub repository of the checkout's `origin`. The bot never creates that repository, records an owner for it, registers it as an app service, deletes it, or offers it as a template. A bot request:

- fast-forwards the live checkout, then runs the round-trip in a separate temporary clone, so the live checkout's ignored `.env` and `.venv` are not replaced;
- asks Copilot to keep the `run` target that starts the bot service and to keep secrets outside the repository;
- commits and pushes the result, then fast-forwards the live checkout;
- reports the commit, change list, and Copilot's final answer, then queues a non-blocking restart of `copilot-telegram-bot.service` through non-interactive `sudo` so the bot comes back with the new code. When other users' sessions are running, the restart waits until the last of them ends, and new sessions are refused until the restart; systemd may terminate the `sudo` call as part of that restart, which is not treated as a failure. When the bot was not started by systemd, it is not restarted and the report asks for a manual restart.

## Configuration

Settings come from `.env` (or the file named by `BOT_ENV_FILE`); real environment variables take precedence. See `.env.example`.

| Setting | Default | Purpose |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | required | Bot token. |
| `TELEGRAM_ADMIN_IDS` | required | Comma-separated numeric ids with full bot access. `TELEGRAM_ADMIN_ID` and `TELEGRAM_OWNER_ID` are accepted aliases. Regular users are approved in the bot instead of being configured. |
| `GITHUB_TOKEN` | required | Used for GitHub API calls and Git over HTTPS through `GIT_ASKPASS` (including private repository clones); it is never written into remote URLs. |
| `GITHUB_OWNER` | token's account | Owner for bare repository names. |
| `REPOS_DIR` | `/home/localadmin/repos` | Parent of app checkouts and local app templates; `eurofish` is the default template. |
| `STATE_DIR` | `~/.copilot-telegram-bot` | Approved users, pending access requests, app ownership, per-user active repositories, administrators' view choices, shared model, app logs, the single-instance lock file, the executable copy of the Git credential helper, and temporary browser-profile copies of parallel sessions. |
| `COPILOT_PROFILE` | `~/.copilot-repo-browser` | Browser profile created by `make login`. |
| `COPILOT_MODEL` | `GPT/GPT-6` | Initial model label; change it later with `/model`. |
| `BOT_SHOW_BROWSER` | `false` | Default browser visibility. An administrator's `browser` or `nobrowser` on `/fix` overrides it for that request. Without `DISPLAY` or `WAYLAND_DISPLAY`, a visible request runs hidden; use VNC or X forwarding to see it. |
| `BOT_TEMPORARY_CHAT` | `true` | Default Temporary chat state. An administrator's `tempchat` or `notempchat` on `/fix` or `/new`, or an administrator's chat-type choice in the guided flows overrides it for that request; disabling it saves the chat in your account. |
| `DEPLOY_SETTLE_SECONDS` | `10` | How long an app's systemd service must remain active to count as a successful start or redeploy. |
| `CLOUDFLARE_API_TOKEN` | empty | Enables `/new` publishing and Cloudflare route management, including `/delete` route cleanup; requires Cloudflare Tunnel Edit and DNS Edit permissions. It is not passed to deployed apps. |
| `CLOUDFLARE_ACCOUNT_ID` | empty | Account containing the tunnel; required with the Cloudflare token. |
| `CLOUDFLARE_ZONE_ID` | empty | Zone containing the public hostname; required with the Cloudflare token. |
| `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL` | Copilot Telegram Bot | Identity on bot commits. |

The engine's selector overrides (`COPILOT_COMPOSER`, `COPILOT_FILE_INPUT`, `COPILOT_SEND`, `COPILOT_DOWNLOAD`, `COPILOT_MODEL_BUTTON`, `COPILOT_NEW_CHAT`, `COPILOT_TEMPORARY_CHAT`, `COPILOT_REASONING`, `COPILOT_STOP`) are CSS selectors read from the bot's environment when Copilot's UI changes. Every request the bot sends, with Temporary chat on or off, starts in a new, empty conversation so that earlier prompts and their archives never add to Copilot's context: after opening Copilot Chat, the engine clicks a visible **New chat** control (the first match of `COPILOT_NEW_CHAT`, or a button or link named New chat; split-button menus are not clicked) and waits until the page shows no earlier conversation, that is, no conversation URL, no user message, and no earlier prompt of this engine outside navigation. If an earlier conversation remains, it reloads the start page once and then fails instead of sending the prompt. To set the chat type, the engine clicks the first visible match of `COPILOT_TEMPORARY_CHAT`, then a visible button, switch, or menu entry labelled Temporary chat; when none appears within a few seconds it also opens popup menus such as new-chat or more-options menus to look for that entry, and it fails only after 30 seconds without one. A **Temporary chat** label on such a control is not read as the active state. Run `python3 engine/copilot_repo_roundtrip.py --help` for the engine's options; its `models` command prints the Claude and GPT models offered by the picker as JSON, and the repeatable `fix --attach <path>` option attaches extra files to the prompt; `fix --no-history` uploads the repository without its Git history.

Without `.env` values or per-request overrides, requests use `nobrowser` and `tempchat`. Telegram options and guided chat-type choices apply only to the request that contains them and take precedence over `.env`.

## Security

- The bot obeys only the Telegram user ids in `TELEGRAM_ADMIN_IDS` and the users an administrator approved; any other user can only send an access request. Administrators can manage every app and infrastructure setting; regular users can execute Copilot-written code only through apps recorded as their own.
- A request can create or change a `Makefile` that the bot then runs. Use a dedicated unprivileged VM user, restrict its passwordless sudo rules to the required service-management commands, restrict the GitHub token to the repositories involved, and keep `.env` and the browser profile readable only by that user.
- Upload only repositories and attachments approved for your organization's Copilot environment. After every prompt, the engine deletes the **Microsoft Copilot Chat Files** folder from the Copilot account's OneDrive and empties its recycle bin, permanently deleting everything in it (see [What a request does](#what-a-request-does)). Each fix upload includes the branch's full Git history, and commit messages include Copilot's outputs; on public repositories these are visible to anyone. Attachments are kept only in a temporary folder under `STATE_DIR` while their request runs; browser-profile copies of parallel sessions hold sign-in state and are likewise kept only under `STATE_DIR` while their session runs.
- Telegram, GitHub, and Cloudflare API tokens are redacted from errors and messages. App units explicitly unset these token variables and `VIRTUAL_ENV`.


The unit tests use fakes for Telegram, GitHub, Copilot, OneDrive, and Cloudflare, and local bare repositories for Git.
